Branch test-ekincare-v2 is checked out. All paths below are working-tree paths on that branch.

Framework
LangGraph (langgraph.graph.StateGraph) with config-driven topology. The graph is not hardcoded in Python — it's assembled from TOML profiles per client/claim-type, with an inheritance mechanism (extends).

Graph builder: backend/app/lang_graph/graph.py — compile_graph() / build_graph(). Uses StateGraph(AgentState), adds nodes from the profile, wires edges and fan_ins (fan-in = LangGraph multi-source edge, i.e. a join/barrier), START -> entry_node, terminal_node -> END. Compiled with a checkpointer (backend/app/lang_graph/checkpointing.py).
Node registry (name → callable): backend/app/lang_graph/registry.py (NODE_REGISTRY).
Profile schema: backend/app/lang_graph/config/models.py (GraphProfile, GraphNode, NodeRuntime, GraphEdge, FanInEdge).
Profile loader (TOML + extends merge): backend/app/lang_graph/config/loader.py.
LLM provider: Google Gemini via Vertex AI, using langchain_google_genai.ChatGoogleGenerativeAI — backend/app/lang_graph/llm/client.py.
Entry point / how it runs: backend/app/services/adjudication.py process_claim() (line ~282) builds initial_state and calls graph.ainvoke(...). It's driven by a Temporal workflow (backend/app/workers/workflows.py, activities.py).

Notes on ekincare-vs-base differences:

Base OPD fans out directly from store_segments; ekincare routes everything through ekincare_policy_extraction_agent first, and adds benefit_plan_agent + fwa_invoice_duplicate (10s timeout) into the audit path.
lab_report_agent / store_lab_report exist in base but ekincare sets lab_report_agent enabled = false (dropped from ekincare fan-ins).
Base OPD wires store_nme_analysis -> audit_agent directly (no benefit_plan, no fwa). Base has no benefit_plan_agent node at all in its edges; ekincare inserts the [benefit_plan_agent, store_icd_codes] -> audit_agent fan-in.
Node types: LLM agent nodes live in backend/app/lang_graph/agents/ and some in nodes/. store_* nodes are DB-persistence nodes. merge_bills, items_categorisation, nme_analysis, build_patient_summary, benefit_plan, validation, fwa_invoice_duplicate, completion are in backend/app/lang_graph/nodes/. No conditional/branching edges — routing is static fan-out + fan-in barriers.

5. How PDFs enter the pipeline
The claim's document is a single PDF referenced by state.file_path (local path; resolved from claim doc_details.storage_key and downloaded — see adjudication.py).
No separate OCR / text-parsing / page-splitting into images. The PDF bytes are base64-encoded and passed natively to Gemini as a {"type": "file", "mime_type": "application/pdf", "base64": ...} message part (Gemini's native PDF/document understanding).
Page selection: backend/app/lang_graph/utils/pdf.py::extract_pages_as_base64(file_path, page_ranges) uses pypdf to build a sub-PDF containing only the pages a given agent needs (page ranges come from segments, e.g. "1-3,7"). If pypdf/splitting fails, it returns the full PDF (robust fallback).
So at the agent boundary, document content = base64 PDF pages (not pre-extracted text, not images). Segregation gets all pages; each extraction agent gets only its document-type's pages; audit gets all non-"other" pages.

Per-claim-type variation comes from flow_configs.py (FlowConfig): OPD uses prescription clinical extractor, OPD-specific audit prompt + policy rules + flash audit model; PP skips consolidated_bills_agent; RM/CL = default.

Important on schemas: These agents do NOT use LangChain structured-output / with_structured_output. Each LLM call passes the PDF (base64 media block) + a system prompt that describes the JSON schema in text, then the raw string response is JSON-parsed (json.loads + json_repair). The Pydantic models in models/ and prompts/schema/ are used for downstream parsing/validation (e.g. _parse_nme_analysis, _parse_patient_summary), not for constraining the LLM output.

The extractor agents (clinical, bills, claim form, bank, IDs) are all built by one factory create_node(document_type, system_prompt, model, ...) in agents/data_extraction_agent.py. Common behavior: read segments["aggregated_segments"][doc_type]["page_ranges"], crop those pages to a base64 sub-PDF via extract_ranges_to_one_pdf_base64(file_path, page_ranges), call process_file_with_llm(...), remap LLM page numbers back to original-PDF numbering, return {EXTRACTED_DATA: [{doc_type: response}], CLAIM_ID}.

3. Dependency graph (for running a subset standalone)
Data flows through the AgentState dict AND through the Postgres DB (store nodes write raw_extracted_data; patient_summary_node and audit_node re-read from DB). To run any node in isolation you must supply its inputs:

segregation → needs only: file_path, claim_id, flow_type, claim_type. Produces segments (aggregated_segments with page ranges) + writes document_segments to DB.
all extractor agents (clinical, itemized/consolidated bills, claim form, bank, IDs) → need: segments (specifically their doc-type page ranges) + file_path. IDs additionally needs patient_name.
bill_merger → needs extracted_data containing itemized_bill and/or consolidated_bill entries.
items_categorisation → needs extracted_data with pharmacy_bills (merger output) + DB ItemCategoryMapping table for fuzzy pass.
nme_analysis → needs extracted_data with categorised_items + claim_id (for provider prompt) + claim_type.
patient_summary → needs claim_id and all per-doc rows already stored in DB (claim form, clinical, bank, ids). It does not read them from state.
audit → consumes nme_analysis_parsed (from store_nme_analysis) + patient_summary_parsed (from store_patient_summary) + segments (or fetches from DB via fetch_segments_from_db) + file_path + claim_type. This is the "audit consumes segregation + NME + patient-summary" relationship the user asked about.
validation → consumes nme_analysis_parsed, patient_summary_parsed, segments.
completion → consumes audit's nme_analysis_parsed/patient_summary_parsed + validation_scores.
So to run e.g. audit standalone without upstream: feed {claim_id, file_path (or file_data), claim_type, nme_analysis_parsed, patient_summary_parsed, segments}. The nme_analysis_parsed must be the post-store NME JSON ({bills:[{bill, items}]}), and patient_summary_parsed the 4-section dict.

4. Segregation agent and Audit agent — full detail
Segregation agent
File: agents/file_segregation_agent.py. Nodes: check_size_node, route_by_size, segregate_half_node, merge_segments_node, segregation_node.
Prompt: DOCS_SEGREGATOR (static, no variables) in prompts/prompts.py. Persona "DocAnalytics-AI". Instructs: identify logical doc boundaries in a merged multi-page PDF, group consecutive same-type pages, emit ONE object per document_type with a compact pages string (e.g. "2-3,8"), is_pharmacy_bill boolean only for itemized_bill. Document-type categories come from DocumentType enum (app/core/enums.py / constants.py): claim_forms, insurance_policy, cheque_or_bank_details, identity_document, hospital_bill, pharmacy_bill, itemized_bill, consolidated_bill, cash_receipt, diagnostic_bill, discharge_summary, laboratory_report, prescription, investigation_report, other, etc.
Model: GEMINI_3_FLASH_MODEL, thinking_level=LOW, budget THINKING_BUDGET. Overridable via FlowConfig.agent_overrides["segregation_agent"].
Schema: models/document_segregator.py DocumentSegregatorResponse (text-described in prompt). Post-processing aggregate_documents (utils/utils.py) → {"aggregated_segments": {doc_type: {page_ranges:[{start,end}], total_pages}}}.
Large-PDF path: if >50 pages, route_by_size uses Send to run segregate_half_node on each half in parallel; each half runs the same LLM prompt on a cropped base64 PDF, then page ranges are offset back to the original numbering and combined in merge_segments_node.
OPD special-case (in segregation_node): merges cash_receipt page ranges into the itemized_bill bucket.
Output/side effect: returns {segments: aggregated_data, claim_id, flow_type}; persists to DB via store_document_segments_with_flow_type (utils/segment_store_helper.py).
Audit agent
File: nodes/audit_nodes.py, function audit_node. Prompt file: prompts/audit.py.
Prompt builder get_audit_prompt(claimed_amount, calculated_total, nme_analysis_json, claim_type, patient_summary_fields, stay_assessment). Selects base prompt from AUDIT_PROMPTS = {"default": AUDIT_SYSTEM_PROMPT, "opd": AUDIT_SYSTEM_PROMPT_OPD} keyed by FlowConfig.audit_prompt_variant, then string-replaces {{CLAIMED_AMOUNT}}, {{CALCULATED_TOTAL}}, {{JSON_OUTPUT}}, {{PATIENT_SUMMARY_FIELDS}}, {{POLICY_RULES}} (from FlowConfig.policy_rules, e.g. policy_rules_opd), {{STAY_ASSESSMENT}}. Prompt is assembled from modular blocks: CORE_PRINCIPLES, CORE_CONTEXT_HEADER, CORE_PATIENT_VERIFICATION, CORE_DUPLICATE_DETECTION, CORE_MISSING_BILL_DETECTION, CORE_DECIMAL_TOLERANCE, CORE_EXAMPLES, plus OPD variants (OPD_MEDICAL_LEGIBILITY, OPD_ICD_EXTRACTION, OPD_CASH_RECEIPT_RULES, etc.).
Model: OPD → GEMINI_3_FLASH_MODEL, else GEMINI_3_PRO_MODEL; thinking_level=MEDIUM, budget 8000.
Inputs: nme_analysis_parsed (parsed to NMEAnalysisData), patient_summary_parsed (→ _parse_patient_summary; flattened via flatten_patient_summary_fields into the 4-section flat dict fed to the prompt), computed claimed_amount (from patient summary) and calculated_total (calculate_total_amount_from_nme_analysis), cleaned_nme_json (prepare_nme_data_for_audit strips categorization_source). The audit PDF is the pages of all doc types except FlowConfig.audit_excluded_doc_types (default: other, investigation_report) and OTHER — extracted via extract_ranges_to_one_pdf_base64; falls back to file_data or full PDF.
Output: LLM returns JSON {analysis:{status, discrepancy_reason,...}, patches:[...], validation:{...}}. Patches applied by apply_audit_patches supporting DELETE_BILL, DELETE_ITEM, EDIT_BILL_DETAILS, EDIT_ITEM, ADD_BILL, ADD_ITEM, EDIT_CLAIMED_AMOUNT, EDIT_PATIENT_SUMMARY (flat-key→section mapping via map_flat_key_to_patient_summary_path). Returns updated nme_analysis_parsed/patient_summary_parsed (edited) + ..._original (pre-audit) + audit_completed, audit_analysis, audit_full_data, audit_patches. Persists raw+parsed as document_type="audit_analysis" in raw_extracted_data.
5. How documents/PDFs enter the pipeline
Source: PDF stored in MinIO; claim_processor.py downloads it to a temp .pdf and passes the local file_path into the graph.
Page utilities in utils/pdf_file_utils.py (uses PyPDF2): get_pdf_page_count, load_pdf_file (whole file → base64), extract_ranges_to_one_pdf_base64(path, page_ranges) (crops given ranges into one combined PDF → base64).
No OCR / no text extraction / no image rasterization. The raw PDF (or a cropped sub-PDF) is sent to Gemini as a multimodal media block: {"type": "media", "data": <base64 pdf>, "mime_type": "application/pdf"} (in process_file_with_llm). Gemini reads the PDF natively. So the format reaching agents is base64-encoded PDF bytes, not text or images.
Page-splitting: (a) >50-page PDFs are split in half for segregation only; (b) each extractor crops just its doc-type page ranges. Because cropping renumbers pages from 1, _remap_page_number / range-offset logic maps LLM-reported page numbers back to original-PDF numbering.
6. State shape
models/state.py. LangGraph state is a TypedDict (LangGraph v1.0+), not Pydantic. Base AgentState(TypedDict, total=False) with custom reducers take_first (claim_id init-once), take_last, and operator.add for list accumulation:

file_path: Union[Dict,str], file_data: Optional[str] (base64, re-extraction), claim_id: Annotated[str, take_first], turn: int, flow_type, claim_type: Annotated[Optional[str], take_last].
Parsed hand-off fields: nme_analysis_parsed, patient_summary_parsed (both Annotated[Dict, take_last]), patient_name.
Audit: audit_analysis, audit_full_data, audit_patches (all take_last).
PDF-split: page_count, half_start, half_end, partial_segments: Annotated[List[Dict], add].
Subclasses: FileSegState (+files_segregated), SegmentProcessState (+segments, extracted_data: Annotated[List[Dict], add], processing_status, validation_scores: take_last), RawDocsStoreState, ExtractedDataState (+extracted_data). The graph is created with StateGraph(AgentState). Note: fan-out branches each append to extracted_data via the add reducer, so the merged state after passthrough contains a list of {doc_type: response} dicts.

Concurrent-write note: because parallel branches write extra keys not covered by reducers (e.g. nme_analysis_stored, per-store booleans), those are simple total=False keys; the load-bearing cross-branch values (nme_analysis_parsed, patient_summary_parsed, validation_scores, audit fields) use take_last.

7. LLM configuration summary
Provider/client: utils/utils.py:load_chat_model(model_name, temperature=0.0, thinking_budget=0, thinking_level=None) → langchain_google_genai.ChatGoogleGenerativeAI with vertexai=True, location="global", project from GOOGLE_CLOUD_CREDENTIALS_JSON service account (cached by SHA256). timeout=settings.LLM_TIMEOUT_SECONDS, max_retries=settings.LLM_MAX_RETRIES.
Model-name format "provider/model"; only gemini provider supported. For gemini-3* models it sets thinking_level (minimal/low/medium); older models use thinking_budget.
Wrapper: utils/llm_utils.py:process_file_with_llm (multimodal PDF) and process_text_with_llm (text). Rate limiter InMemoryRateLimiter(10 rps); retry/backoff on 429/500/503; continuation loop for MAX_TOKENS (up to MAX_CONTINUATIONS=12) using truncate points + `previous_json` re-injection; response cleaned via clean_json_response + json_repair.
Temperature is globally 0.0 (DEFAULT_TEMPERATURE) — never overridden per agent.
Per-agent model config: set at node construction in data_extraction_agent.py (e.g. bills → 2.5-flash budget 8000; discharge/prescription/bank → 3-flash; claim form/IDs → 2.5-flash budget 0), and inside nodes for segregation (3-flash LOW) and audit (3-flash OPD / 3.1-pro non-OPD, MEDIUM). Overrides per claim type via FlowConfig.agent_overrides (AgentConfig supports system_prompt, continuation_prompt, continuation_system_prompt, model, thinking_budget, thinking_level) — currently used for audit_agent (OPD→flash) and available for segregation_agent.
Cost/usage tracking: every invocation logged + persisted to claim_llm_usage via pricing/estimated_vertex_cost.py + pricing/rate_card_resolve.py (vertex_rate_card.json), gated by settings.ENABLE_LLM_USAGE_PERSISTENCE.
